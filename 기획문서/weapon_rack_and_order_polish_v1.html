1. 보관함 흡수 연출 - 축소 애니메이션 제거수정

현재: CarryStack.DepositFlightRoutine이 재료(목재/광물/마석)가 보관함으로 날아가는 동안 localScale을 1 → 0.1로 점점 줄임.

조치: 이 스케일 축소 라인만 제거. 포물선 비행 + 회전은 그대로 두고, 도착 시점에 그대로 사라짐(despawn). 무기가 판매대에 적립될 때도 같은 루틴을 타서 동일하게 적용됨.

2. 무기 랙(WeaponRack) 신설신규 메커닉

현재 문제

QUICK CRAFT 완료 즉시 CraftingStation.ApplyCraft가 CarryStack.TryAdd를 직접 호출해서 플레이어 등짐으로 순간이동하듯 흡수됨 - 별도 픽업 동작이 없음. 또한 "손에도 안 쌓이는 현상"은 같은 프레임에 여러 개(amount>1)를 동시에 TryAdd 호출하면서 코루틴들이 겹쳐 타이밍이 꼬이는 것으로 추정.

변경안

대장간 출력 위치(기존 WeaponOutputPosition 자리)에 WeaponRack 컴포넌트를 런타임 생성(이 프로젝트의 InteractionPadIndicator.Attach와 같은 "위성 오브젝트" 패턴). 제작 완료 시 무기는 이제 플레이어가 아니라 랙에 쌓임(선반 위에 실제로 보이는 더미). 플레이어가 랙의 픽업 반경(기본 2m) 안에 들어와 있을 때만 보관함/판매대와 동일한 컨베이어 방식(한 개씩, 처음엔 느리게 점점 빨라짐)으로 랙 → 등짐으로 이동.

참고: 대장간 상호작용 반경(2.5m)이 랙 반경(2m)보다 넓어서, 보통은 제작 직후 이미 랙 픽업 범위 안에 서 있는 상태 - 실사용에서는 "만들자마자 등에 실리는" 흐름과 크게 다르지 않게 느껴지되, 구조적으로는 랙 → 픽업이라는 별도 단계가 실제로 존재함.

CarryStack 쪽 변경: 이미 스폰된(랙에 쌓여있던) 아이템을 그대로 등짐으로 편입시키는 TryReceiveExisting(Transform, CarryLayer) 신설 - 기존 TryAdd처럼 새로 스폰하지 않고, 드롭 연출 없이 바로 비행 단계로 들어감(랙에서 이미 "놓여있던" 상태이므로).

3. 손님 말풍선에 무기 실루엣 추가신규 + 범위 확인 필요

확인된 사실: CustomerOrder에는 무기 종류 필드가 아예 없음 - v7 설계가 "등급/종류 무관, 개수만" 요구하도록 의도적으로 단순화했고, 실제로 QUICK CRAFT도 항상 고정된 한 가지 quickCraftWeaponType(기본 검)만 판매대로 보냄. 즉 지금은 손님마다 원하는 무기 "종류"가 다른 게 아니라 전부 같은 것을 원함.

이번에 하는 것: 말풍선에 무기 실루엣 아이콘 1종(검 모양, UIShapes에 신설)을 개수 텍스트 옆에 추가 - 시각적 정보 보강.

하지 않는 것 (범위 밖): "손님마다 다른 무기 종류를 요구하고, 실루엣으로 구분해서 보여준다"는 해석이라면 CustomerOrder에 타입 필드 추가 + QUICK CRAFT의 단일 타입 제약 해제 + TryFulfill 타입 매칭까지 필요한 더 큰 작업이라, v7의 "등급/종류 무관" 결정을 뒤집는 것이라 별도로 다시 확인 후 진행하는 게 맞다고 판단 - 이번엔 실루엣만 추가.

4. 인내심 바 제거정리

확인된 사실: 코드에 "인내심" 로직/바 자체가 없음(v6에서 이미 개념 삭제, OrderQueueManager 주석에도 "No patience/time limit" 명시). 다만 Customer의 말풍선에 있는 배달 진행률 바(progressFillImage, "1/3" 텍스트 아래 채워지는 바)가 인내심 게이지처럼 보여서 혼동하신 것으로 추정.

조치: 이 진행률 바를 제거하고 텍스트("1/3")만 남김 - 정보 손실 없이 바 형태의 UI만 사라짐.

5. 주문 초과 지급 버그코드상 원인 불명확 - 추정 수정

코드 확인 결과: OrderQueueManager.TryFulfill()은 호출 1회당 remaining = RequestedCount - DeliveredCount로 상한을 계산해서, 이 상한을 절대 넘지 않도록 이미 막혀 있음 - 즉 "손님 1명이 2개 요청했는데 5~6개를 받는" 것은 이 메서드 하나만 보면 구조적으로 일어날 수 없음.

유력 원인 추정: 말풍선 탭에 쿨다운이 전혀 없어서, 연속 탭 한 번의 "순간"에 앞 손님 주문이 완료 → 큐가 바로 한 칸씩 당겨짐 → 다음 손님 주문까지 곧바로 처리되는 일이 반복되면서, 실제로는 여러 손님이 눈 깜짝할 새 연달아 처리된 것이 "한 손님이 초과로 받는 것"처럼 보였을 가능성이 높음(주문당 1~3개로 적어서 한 탭에 한 주문이 통째로 끝나는 게 원래 의도).

조치: TryFulfill 성공 시 짧은 쿨다운(0.4초) 부여 - 연속 탭으로 여러 주문이 순식간에 연쇄 처리되는 것을 막음. 다만 이건 코드 분석 기반 추정 수정이라, 수정 후 Play Mode에서 실제로 재현되는지 다시 확인할 예정.
